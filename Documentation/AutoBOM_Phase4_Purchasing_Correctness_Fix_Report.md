## 2. Artifact freshness/state model

Nine tracked artifacts, five states each (`current`, `stale`, `not_generated`,
`failed`, `not_required`), stored in `response["artifact_status"]`:

- **File artifacts** (`FILE_ARTIFACT_KEYS`): `cleaned_csv`, `sourcing_report`,
  `digikey_list_csv`, `partsbox_import_csv`, `run_summary` — each
  independently re-exported by `regenerate_purchasing()`.
- **Permanent artifacts** (`PERMANENT_ARTIFACT_KEYS`): `cleaned_workbook`,
  `partsbox_unmatched_csv` — never regenerated by `regenerate_purchasing()`;
  once marked stale by a mutation they stay stale forever (see §7/§8).
- **Supplier artifacts** (`SUPPLIER_ARTIFACT_KEYS`): `mouser_cart`,
  `digikey_mylist` — external, side-effecting; skipped entirely when
  already `current` (see §5/§6).

`stale_after_mutation` remains as a **derived convenience flag**
(`_recompute_global_stale_flag()`), computed as "any file or supplier
artifact is stale" — it deliberately excludes the two permanent artifacts so
the page doesn't report "Stale" forever once everything regeneratable has
recovered. A Needs Review mutation (Retry Exact / replacement) calls
`_mark_artifacts_stale_if_current()`, which flips only artifacts that were
`current` to `stale` — anything already `not_generated`/`failed`/
`not_required` is left alone.

## 3. Purchasing readiness rules

`derive_purchasing_status()` now computes per-supplier requirement via
`_supplier_requirement()` — the exact same `build_mouser_cart_items()` /
`build_digikey_mylists_parts()` selection logic used to actually build the
cart/list. A supplier with zero required items is excluded from the
readiness check entirely.

Order of evaluation: `Not Available` → `Stale — BOM Changed` (any
regeneratable artifact stale) → `Needs Review` → then, over the set of
*required* supplier artifacts: `Not Yet Generated` (none attempted),
`Generation Failed` (all required failed), `Partial — Generation Failed`
(some but not all failed), `Ready for Handoff` (all required current).
`attempted=True, created=False` is always treated as `failed`, never as
ready — attempted is not the same as ready.

If neither supplier is required at all, status is `Not Yet Generated` until
an explicit regeneration has actually run at least once
(`purchasing_regenerated_at_least_once`), then `Ready for Handoff` — so a
completely untouched fresh run doesn't read as trivially "ready".

## 4. Partial-success handling

`regenerate_purchasing()` wraps every stage (cleaned CSV, sourcing report,
DigiKey list CSV, PartsBox import CSV, Mouser cart, DigiKey MyList, run
summary) in its own try/except and records its own `artifact_status` entry.
A failure in one stage never blocks or falsely marks another. Example:
Mouser succeeds and DigiKey raises → `mouser_cart: current`,
`digikey_mylist: failed`, overall status `Partial — Generation Failed`, and
`result["purchasing"]["mouser"]` keeps its real CartKey.

## 5. Supplier-specific retry behavior

Before attempting a supplier artifact, `regenerate_purchasing()` checks: not
required → `not_required` (skip); already `current` → skip entirely (no
re-invocation, message noted); otherwise attempt (or leave status unchanged
if the caller didn't request that supplier this cycle / the feature flag is
off). A retry that only needs DigiKey does not recreate an already-current
Mouser cart, and vice versa — verified by
`test_retry_after_partial_failure_does_not_recreate_successful_supplier_artifact`.

## 6. Duplicate-artifact prevention

Vendor creation calls only happen inside `regenerate_purchasing()`, which is
only invoked from the "Regenerate Purchasing" button handler in `app.py` —
never from page load or a plain rerun. `test_plain_rerun_creates_no_vendor_artifact`
and `test_one_explicit_regeneration_click_creates_each_required_artifact_at_most_once`
cover this directly; the already-current skip in §5 additionally prevents a
second click (or a retry for the other supplier) from creating a duplicate
cart/list for a supplier that already succeeded.

## 7. Workbook policy

`cleaned_workbook` is a `PERMANENT_ARTIFACT_KEYS` member. It is set
`current` only at the end of a fresh `run_bom_workflow()` (built with that
run's real `column_mapping`/`warnings` DataFrames). `regenerate_purchasing()`
never touches it. Once a mutation marks it `stale`, it stays `stale`
indefinitely — no fabricated sheets, no silent re-enable. Verified by
`test_stale_workbook_remains_unavailable_after_other_artifacts_regenerate`
and the UI-level `test_download_buttons_disable_and_reenable_per_artifact_after_regeneration`.

## 8. PartsBox unmatched-file policy

`partsbox_unmatched_csv` is the other `PERMANENT_ARTIFACT_KEYS` member, for
the same reason: regenerating it correctly requires a fresh, side-effecting
PartsBox `project/get-entries` comparison that `regenerate_purchasing()`
deliberately does not re-run. Once stale, it stays disabled rather than
being silently re-enabled with data that may not reflect current PartsBox
state. Verified by `test_partsbox_unmatched_csv_regenerated_or_remains_unavailable`.

## 9. Export failure handling

Every export stage in both `run_bom_workflow()`'s initial run and
`regenerate_purchasing()` is independently guarded (pre-existing try/except
for the initial run's supplier/PartsBox steps; newly added, per-stage
try/except throughout `regenerate_purchasing()`, closing the gap the review
identified — cleaned CSV regeneration was previously the one stage outside
any try/except). A failure records `artifact_status[key] = "failed"` and an
entry in `purchasing_regeneration_errors`, and never raises out of
`regenerate_purchasing()`, never mutates canonical BOM state, and never
marks an unrelated artifact `current`. Verified by
`test_cleaned_csv_failure_is_caught_and_reported`,
`test_one_export_failure_keeps_only_that_artifact_stale_or_failed`, and
`test_stale_downloads_never_become_enabled_merely_because_another_artifact_succeeded`.

## 10. Structured vendor result retention

`_build_mouser_purchasing()` / `_build_digikey_purchasing()` no longer embed
the full raw vendor response (`raw_result` / `raw_create_result` /
`raw_add_result`) in `response["purchasing"]`. They return only the
structured fields the app uses (Mouser: attempted/created/items_count/
cart_key/message; DigiKey: attempted/created/list_id/list_name/share_id/
parts_count/message). Raw payloads are kept in-memory only, in
`response["_purchasing_raw"]` — a key starting with `_`, which
`_write_run_summary()`'s existing filter already excludes from the JSON
written to disk. No secrets were ever placed in these payloads; this change
is about reducing what's retained/persisted, not patching a leak.

## 11. Tests added

`tests/test_purchasing_state.py` (rewritten, 28 tests total, up from 15) adds:
partial regeneration (Mouser success/DigiKey failure and the reverse), retry
after partial failure preserves the successful artifact, required supplier
with `created=False` is not ready, supplier with zero required items needs
no artifact, both required suppliers succeeding → Ready for Handoff, cleaned
CSV failure caught and reported, one export failure isolated to that
artifact, stale workbook stays unavailable after other artifacts recover,
PartsBox unmatched CSV stays unavailable, stale downloads never re-enabled
by an unrelated success, one click creates each required artifact at most
once, plain rerun creates nothing, purchasing item counts always derive
from the live canonical BOM.

`tests/test_app_smoke.py` adds a UI-level test that a mutation disables both
cleaned CSV and workbook downloads, and that clicking Regenerate re-enables
only cleaned CSV (workbook stays disabled).

`tests/test_partsbox_lifecycle.py` adds tests for `storage_has_tag()`
(case/whitespace-insensitive matching, `None` input) and a guard that
`app.py` imports and calls the shared helper rather than reimplementing the
check inline.
